Entry 설계
1. Entry안에 들어았는것
    * message - 커밋 메세지
    * author - 작성자
    * parents - 부모 노드
    * timestamp - 작성 시간
    * hash - 해시값

    ++ 왜 hash_next가 없을까?
        - 이전 mini Redis에서는 Entry에 hash_next가 있었다. 하지만 지금 Entry설계에는 존재하지않는다
        - mini Redis에서는 Entry를 여러가지 자료구조에서 포인터가 돌려써  Entry안에 넣었지만, 현재 구조에서는 Entry를 hashmap만 사용하기 때문에 hash_next는 hashmap안에 구현한다.

2. 실제 git 해시값 계산 방법
    * 기존의 git은 SHA-1의 암호형 해시 함수를 사용합니다
        - 코드 조작방지: 해커가 소스코드를 악의적으로 수정하는것을 예방
        - 눈사태효과 필요: 커밋 하나, 시간 하나만 바뀌어도 변조여부를 바로 파악 가능
        - 고유한 ID보장

    * 16진수로 문자 40개표시
        -> 16진수(4비트) * 40자리 = 160비트
        -> SHA-1의 크기 = 160비트 = 20바이트

    * 실제 git에서는 40자리를 다 칠 수 없기 때문에 앞에 7자리만 때서 검색,삭제 등 가능(저장되는건 40자리 다 저장됨)
    
3. 내 코드 해시값 계산 방법
    위에서 말했다싶이 기존git은 40자리 저장하고 사람에게 보여줄떄 7자리로 보여준다.
    -> 하지만, 현재 구현 하는 mini git 프로그램은 40자리까지 가지고 있을 필요가 없다
        왜냐하면 커밋의 개수가 얼마나 커질지 직접 설정하기 때문에 에측 가능한 범위임
        SO. 뒤에 36자리는 버리고 4자리만 hash에 저장

        4자리면 충돌이 안일어나나요?

        30개	    0.684%
