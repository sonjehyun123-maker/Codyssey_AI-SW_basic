# Mini Git

Git의 커밋 그래프(DAG), 해시맵, 위상 정렬, BFS 최단 경로, 역색인, 병합 정렬을 직접 구현한 CLI 기반 Mini Git.

## 1. 프로젝트 개요

- **목표**: Git 내부 구조(커밋 그래프, 해시)를 자료구조/알고리즘 학습 도구로 재구현
- **범위**: 보너스 과제(diff, merge, 정렬 알고리즘 성능 비교) 제외
- **실행 환경**: Python 3.10 이상
- **실행 방법**
  ```
  python main.py
  ```
- **제약사항 준수**
  - 그래프 전용 라이브러리 미사용
  - `sorted()`, `list.sort()` 미사용 → 병합 정렬 직접 구현
  - 파일 저장/네트워크 통신 없음 (세션 내 메모리 동작)

## 2. 학습 내용

### 2-1. 암호학적 해시 (SHA-1)

커밋 hash는 `message + author + parents + timestamp`를 SHA-1에 통과시킨 결과다. 카운터 기반(단사함수, 구조적으로 충돌 불가능) 대신 SHA-1을 선택한 이유는 두 가지다.

- **Content-Addressable Storage**: 내용이 곧 주소를 결정한다는 Git의 핵심 철학을 직접 체감하기 위함
- **눈사태 효과**: 입력이 1글자만 바뀌어도 출력이 완전히 달라지는 성질을 실습으로 확인

카운터가 실무에서 불가능한 이유는, Git이 중앙 서버 없이 여러 개발자가 독립적으로 커밋을 생성하는 분산 환경이기 때문이다. 순서를 매기는 중앙 존재가 없으니 "내용 기반"으로 각자 독립 계산해도 충돌이 드문 해시 방식이 필요하다.

### 2-2. 해시 자릿수 결정

실제 Git 기본 축약 길이는 7자리(28비트)다. 이는 대규모 분산 저장소(수백만 커밋)를 가정한 값이다. Mini Git은 세션당 커밋 수가 수십 개 이내로 제한적이므로, 생일 문제(birthday paradox) 근사식(`1 - e^(-n²/2m)`)으로 자릿수별 충돌 확률을 계산해 최솟값을 선택했다.

| 자릿수 | 커밋 10개 | 커밋 30개 |
|---|---|---|
| 3자리 | 1.21% | 10.40% |
| **4자리 (채택)** | **0.076%** | **0.684%** |
| 6자리 | 0.0007% | 0.007% |

### 2-3. 해시 충돌 처리

프로젝트 규모(4자리, 65,536개 공간)에서는 낮지만 0은 아닌 충돌 확률이 존재한다. 실제 Git(160비트, 공간이 사실상 무한대에 가까움)이 별도 충돌 처리 로직 없이 동작하는 것과 달리, Mini Git은 표시 자릿수를 의도적으로 줄였기 때문에 그 대가로 아래 로직이 필요하다.

- `Commit`은 SHA-1 전체 결과(40자리, `full_hash`)를 항상 보관하고, 화면/키로 쓰는 `hash`는 그중 앞 `hash_length`자리(초기값 4)만 사용
- `HashMap.put()`에서 삽입 전 동일 hash 존재 여부를 확인하고, 충돌 시 `Commit.extend_hash()`로 자릿수를 1씩 늘려 재계산 없이 더 긴 접두사를 사용
- SHA-1을 다시 계산하지 않고 이미 확보된 40자리에서 슬라이싱만 늘리는 방식이라, 실제 Git이 저장소 크기에 따라 표시 자릿수를 자동으로 늘리는 동작과 유사한 접근이다

### 2-4. 위상 정렬 기반 LOG

`LOG`는 최신순이 아니라 부모가 자식보다 먼저 출력되어야 한다는 요구사항 때문에, 전체 커밋을 순회하며 방문하지 않은 커밋에 대해 부모를 먼저 재귀 방문한 뒤(post-order) 결과 리스트에 추가하는 DFS 방식을 사용했다.

- 커밋 그래프는 merge 기능(보너스, 미구현)이 없는 현재 구조상 사이클이 발생할 수 없다고 가정하고 작성했다. 순환 그래프에 대한 별도 방어 로직(방문 스택 기반 사이클 감지)은 포함하지 않았다.

### 2-5. BFS 기반 최단 경로

`PATH`는 스펙상 "커밋-부모 연결을 무방향 간선으로 간주했을 때 간선 수 최소"로 정의된다. 모든 간선의 가중치가 동일(1)한 상황이므로, 가중치가 다른 그래프에 쓰이는 다익스트라 대신 BFS만으로 최단 경로를 구할 수 있다. 여러 최단 경로가 있을 경우 사전순으로 가장 작은 경로를 고르기 위해, 이웃 노드를 정렬해서 확장하고 동일 길이 후보들을 모아 마지막에 문자열 비교로 최종 선택한다.

### 2-6. 병합 정렬 (Merge Sort)

`sorted()` 사용 금지 제약에 따라 병합 정렬을 직접 구현했다. 버블/삽입 정렬(O(n²), 느림) 대신, 퀵/힙 정렬(O(n log n)이지만 안정 정렬이 아님) 대신 병합 정렬을 택한 이유는 **안정 정렬이면서 항상 O(n log n)**인 유일한 조합이기 때문이다. `LOG --sort-by=author`에서 같은 작성자의 커밋들이 원래 생성 순서를 유지해야 한다는 요구를 만족하려면 안정성이 필요하다.

### 2-7. 역색인 (Inverted Index)

`keyword → [commit_hash, ...]`, `author → [commit_hash, ...]` 두 개의 딕셔너리로 구현했다. 커밋 생성(`COMMIT`) 시점에 즉시 갱신되어, `SEARCH`가 전체 커밋을 순회하지 않고 O(1)에 가까운 조회로 후보를 가져올 수 있다.

## 3. 코드 설명

| 파일 | 역할 |
|---|---|
| `entry.py` | `Commit` 클래스. message/author/parents/timestamp/hash 5개 필드, SHA-1 해시 생성 및 자릿수 확장 |
| `hashmap.py` | `Node`(체이닝 래퍼) + `HashMap`(djb2 스타일 해시 함수, 체이닝 충돌 처리, put 시 hash 중복 검사) |
| `repository.py` | 저장소 상태 관리: `branches`(브랜치→커밋 hash), `head`, `current_user`. INIT/BRANCH/SWITCH/COMMIT 담당 |
| `graph.py` | DAG 탐색: `log`(위상 정렬), `ancestors`(BFS 조상 탐색), `path`(BFS 최단 경로 + 사전순 선택) |
| `index.py` | `InvertedIndex`: keyword/author 역색인 |
| `sort.py` | 병합 정렬 + date/author 비교 함수 |
| `main.py` | REPL 루프, 명령어 파싱(`shlex`), 명령어 라우팅 테이블, 출력 포맷 |

**설계 결정 하나 짚어두면**: `Commit`은 해시맵 체이닝용 포인터(`hash_next`)를 직접 갖지 않는다. Mini Redis 프로젝트에서는 Entry가 해시맵+LRU 두 자료구조에서 동시에 쓰여 포인터 공유가 효율적이었지만, Mini Git은 Commit이 해시맵 한 곳에서만 저장 목적으로 쓰이므로 그 이점이 없다. 대신 `hashmap.py`에 별도 `Node` 래퍼를 둬서 `Commit`은 순수 도메인 데이터로, 체이닝 책임은 `Node`로 분리했다.

## 4. 명령어 정리 및 로직

| 명령어 | 문법 | 로직 |
|---|---|---|
| `INIT` | `init <user_name>` | `main` 브랜치 생성(hash는 아직 없어 `None`), HEAD를 `main`으로 설정 |
| `BRANCH` | `branch <name>` | 현재 HEAD가 가리키는 커밋 hash를 그대로 복사해 새 브랜치 생성 |
| `SWITCH` | `switch <name>` | HEAD를 지정 브랜치로 이동. 없는 브랜치면 `Unknown branch: <name>` |
| `COMMIT` | `commit "<msg>"` | 현재 HEAD 커밋을 parent로 새 Commit 생성 → hashmap 저장(충돌 시 자동 확장) → 역색인 갱신 → 브랜치 갱신 |
| `LOG` | `log` | DFS로 부모 우선 출력(위상 정렬 성격) |
| `LOG --sort-by` | `log --sort-by=date\|author` | 병합 정렬로 전체 커밋 정렬 (위상 순서 대신 값 기준) |
| `PATH` | `path <hash1> <hash2>` | 무방향 BFS 최단 경로, 여러 개면 사전순 최소, 없으면 `No path` |
| `ANCESTORS` | `ancestors <hash>` | BFS로 도달 가능한 모든 조상 hash 수집 후 정렬 출력 |
| `SEARCH` | `search <keyword>` 또는 `search --author=<name>` | 역색인 조회 |

**공통 규칙**: 명령어 대소문자 무시, 따옴표 포함 인자는 `shlex.split`으로 파싱, `EXIT`/`QUIT`로 종료, 잘못된 인자는 `Invalid args`.

## 5. 추가 학습 및 한계

- **대규모 확장 시 병목**: 현재 해시맵은 버킷 개수(기본 16)가 고정이며 리해시(rehash)를 구현하지 않았다. 세션당 커밋 수십 개 규모에서는 평균 체인 길이가 짧아 성능 영향이 미미하다고 판단했다. 참고로 실제 Git도 전통적인 동적 리사이징 해시맵을 쓰지 않는다 — 해시 앞 2자리를 디렉토리로 쓰는 고정 256버킷 구조(loose object)와, 커밋이 쌓이면 정렬된 인덱스 파일로 압축해 이진 탐색을 쓰는 방식(packfile)을 쓴다. 향후 대규모 확장을 고려한다면 리해시보다는 이 방식을 참고하는 편이 더 적절하다.
- **해시 재현성**: `timestamp`가 hash 계산에 포함되어 있어, 동일한 message/author/parents로 커밋을 여러 번 만들어도 매번 다른 hash가 나온다. 이는 의도된 설계로, 완전히 동일한 내용의 커밋이 hash 충돌 없이 별개로 기록될 수 있게 한다. 다만 이 때문에 동일 입력에 대한 결정론적 테스트(같은 시나리오 재실행 시 같은 hash 기대)는 불가능하며, 테스트 코드 작성 시에는 hash 값 자체보다 커밋 개수/관계/메시지 등을 검증 기준으로 삼아야 한다.
- **사이클 안전성**: `LOG`의 DFS 방문 로직은 커밋 그래프에 사이클이 없다는 가정(merge 미구현으로 구조상 사이클 발생 불가) 위에 작성되었다. 향후 merge(보너스)를 구현해 다중 부모가 늘어나도, 부모 방향으로만 순회하는 DAG 특성상 사이클은 발생하지 않는다.
- **동률 처리**: `LOG --sort-by`에서 값이 같은 커밋들은 병합 정렬의 안정성 덕분에 원래 생성 순서를 유지한다. 별도의 추가 정렬 키(예: hash 사전순)는 두지 않았다.
