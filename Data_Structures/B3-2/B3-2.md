# Mini Git

Git의 커밋 그래프(DAG), 해시맵, 위상 정렬, BFS 최단 경로, 역색인, 병합 정렬을 직접 구현한 CLI 기반 Mini Git.

## 1. 프로젝트 개요

- **목표**: Git 내부 구조(커밋 그래프, 해시)를 자료구조/알고리즘 학습 도구로 재구현
- **범위**: 보너스 과제(diff, merge, 정렬 알고리즘 성능 비교) 제외
- **실행 환경**: Python 3.10 이상
- **실행 방법**
  ```
  python main.py
  ```
- **제약사항 준수**
  - 그래프 전용 라이브러리 미사용
  - `sorted()`, `list.sort()` 미사용 → 병합 정렬 직접 구현
  - 파일 저장/네트워크 통신 없음 (세션 내 메모리 동작)

## 2. 학습 내용

### 2-1. 암호학적 해시 (SHA-1)

커밋 hash는 `message + author + parents + timestamp`를 SHA-1에 통과시킨 40자리 16진수 결과다. 카운터 기반(단사함수, 구조적으로 충돌 불가능) 대신 SHA-1을 선택한 이유는 두 가지다.

- **Content-Addressable Storage**: 내용이 곧 주소를 결정한다는 Git의 핵심 철학을 직접 체감하기 위함
- **눈사태 효과**: 입력이 1글자만 바뀌어도 출력이 완전히 달라지는 성질을 실습으로 확인

카운터가 실무에서 불가능한 이유는, Git이 중앙 서버 없이 여러 개발자가 독립적으로 커밋을 생성하는 분산 환경이기 때문이다.

### 2-2. 저장은 40자리, 조회는 4자리 (실제 Git과 동일한 구조)

`Commit.hash`는 **항상 40자리 전체**를 저장한다. 명령어 인자로 입력받는 값은 앞 4자리(`SHORT_LENGTH`)여도 되지만, 화면 표시 방식은 명령어마다 다르다.

- 저장(`entry.py`, `hashmap.py`): 40자리 그대로 계산·저장·`parents` 연결에 사용
- 표시: `LOG`/`ANCESTORS`는 실제 `git log`(옵션 없는 기본형)와 동일하게 **40자리 전체**를 그대로 보여준다. `COMMIT` 확인 메시지·`PATH`·`SEARCH`는 `short_hash()`로 앞 4자리만 잘라서 보여준다(실제 Git이 `[main abc1234] message` 같은 커밋 확인 줄에서 짧은 hash를 쓰는 것과 동일한 관례)
- 입력(`main.py`의 `resolve_hash()`): 화면에 몇 자리가 찍혀 있든, 사용자가 입력한 짧은 접두사를 저장된 40자리 중 그 접두사로 시작하는 커밋을 찾아 원래 값으로 되돌린다
  - 매칭 0개 → `Unknown commit: <입력값>`
  - 매칭 2개 이상 → `Ambiguous commit: <입력값> matches N commits`
  - 매칭 1개 → 해당 커밋으로 확정

이 구조는 실제 Git이 40자리 SHA-1을 항상 저장하면서, 명령어별로 다른 길이의 hash를 보여주는 것과 동일한 원리다(기본 `git log`는 전체 40자리, `git log --oneline`이나 커밋 확인 줄은 짧은 hash). 40자리 공간(2^160)에서는 충돌 확률이 사실상 0에 가까워, 이전 설계(트러블슈팅 문서 7-2절 참고)에서 필요했던 자동 충돌 회피 로직이 더 이상 필요 없다.

### 2-3. 해시맵 버킷 설계 — 접두사를 직접 버킷 번호로

```python
def _hash_index(self, key):
    return int(key[:2], 16)
```

버킷 개수는 `16^2 = 256`개이고, key(40자리 hash)의 **앞 2자리를 그대로 버킷 번호로 사용**한다. djb2 같은 별도 해시 함수를 쓰지 않는 이유는, SHA-1 출력이 이미 암호학적으로 균등 분포하도록 설계되어 있어 추가로 섞을 필요가 없기 때문이다(일반적인 임의 문자열 key라면 djb2 같은 믹싱 함수가 필요하지만, 이미 균등한 SHA-1 결과에는 불필요한 중복 연산이다).

이 구조는 실제 Git의 loose object 저장 방식(`.git/objects/xx/yyyy...`, 앞 2자리를 디렉토리명으로 씀)과 원리가 같다. 짧은 접두사(2자리 이상)로 조회할 때 해당 버킷 하나만 확인하면 되므로, `find_by_prefix()`의 평균 비용이 전체 순회(O(n))에서 **해당 버킷 내부만 순회(평균 O(n/256))**로 줄어든다.

버킷 자체가 겹치는 것(앞 2자리가 같은 서로 다른 커밋)은 정상적으로 발생하며 체이닝(`Node.next`)으로 해결한다. 이는 "짧은 접두사가 여러 커밋에 매칭되는 문제"(위 2-2절, `Ambiguous commit`)와는 다른 층위의 문제로, 버킷 충돌은 저장 단계에서 체이닝이 항상 해결하고, 접두사 모호성은 조회 단계에서 사용자에게 알려 더 긴 입력을 요구한다.

### 2-4. 위상 정렬 기반 LOG — 리프에서 시작해 브랜치별로 그룹핑

`LOG`는 최신순이 아니라 부모가 자식보다 먼저 출력되어야 한다는 요구사항 때문에, 방문하지 않은 커밋에 대해 부모를 먼저 재귀 방문한 뒤(post-order) 결과 리스트에 추가하는 DFS 방식을 사용했다.

바깥 루프가 어떤 순서로 커밋을 방문 시작하는지가 "서로 다른 브랜치끼리의 상대 순서"를 결정한다. 리프(다른 커밋의 parent로 참조되지 않는 커밋, 즉 각 브랜치의 tip)를 먼저 찾고, 그 리프들을 생성 시간순으로 정렬한 뒤, 각 리프에서 시작해 조상 전체를 한 번에 끌어오는 방식을 쓴다. 이렇게 하면 한 브랜치의 커밋들이 결과 안에서 서로 흩어지지 않고 연속으로 묶여 나온다(브랜치 A의 커밋들이 다 나온 뒤에야 브랜치 B의 커밋들이 시작됨) — 실제 Git의 `--topo-order`가 브랜치 줄기를 안 섞는 것과 같은 효과다. 리프 정렬에는 이미 구현된 `sort_by_date()`를 재사용했다(2-6절, 7-6절 참고).

- 커밋 그래프는 merge 기능(보너스, 미구현)이 없는 현재 구조상 사이클이 발생할 수 없다고 가정하고 작성했다.
- 부모가 없는 두 커밋(예: 커밋 없는 상태에서 만든 브랜치 각각의 첫 커밋)은 서로 아무 인과관계도 없으므로, 어느 쪽 브랜치 그룹이 먼저 나올지는 순수하게 리프 날짜로 결정된다.

### 2-5. BFS 기반 최단 경로

`PATH`는 스펙상 "커밋-부모 연결을 무방향 간선으로 간주했을 때 간선 수 최소"로 정의된다. 모든 간선의 가중치가 동일(1)한 상황이므로 BFS만으로 최단 경로를 구할 수 있다. `Commit.parents`는 자식→부모 한 방향만 저장하지만(부모가 만들어지는 시점엔 자식이 아직 존재하지 않아 반대 방향 참조가 원천적으로 불가능하다), `PATH` 계산 시에만 `build_undirected_graph()`가 부모→자식 방향까지 추가한 **일회용 양방향 사본**을 만들어 사용한다. 원본 `parents`는 건드리지 않으므로 `LOG`/`ANCESTORS`의 방향성은 그대로 유지된다.

### 2-6. 병합 정렬 (Merge Sort)

`sorted()` 사용 금지 제약에 따라 병합 정렬을 직접 구현했다. 병합 정렬을 택한 이유는 **안정 정렬이면서 항상 O(n log n)**인 유일한 조합이기 때문이다. `LOG --sort-by=author`에서 같은 작성자의 커밋들이 정렬 전후로 상대 순서가 뒤바뀌지 않아야 한다는 요구를 만족하려면 안정성이 필요하다.

### 2-7. 역색인 (Inverted Index)

`keyword → [commit_hash, ...]`, `author → [commit_hash, ...]` 두 개의 딕셔너리로 구현했다. 커밋 생성(`COMMIT`) 시점에 즉시 갱신되어, `SEARCH`가 전체 커밋을 순회하지 않고 O(1)에 가까운 조회로 후보를 가져올 수 있다.

## 3. 코드 설명

| 파일 | 역할 |
|---|---|
| `entry.py` | `Commit` 클래스. message/author/parents/timestamp/hash(40자리 전체) 5개 필드 |
| `hashmap.py` | `Node`(체이닝 래퍼) + `HashMap`(앞 2자리 직접 버킷 인덱스, 256버킷, `find_by_prefix`로 접두사 조회) |
| `Repository.py` | 저장소 상태 관리: `branches`(브랜치→커밋 hash), `head`, `current_user`. INIT/BRANCH/SWITCH/COMMIT 담당 |
| `graph.py` | DAG 탐색: `log`(위상 정렬), `ancestors`(BFS 조상 탐색), `path`(BFS 최단 경로 + 사전순 선택) |
| `git_index.py` | `InvertedIndex`: keyword/author 역색인 |
| `sort.py` | 병합 정렬 + date/author 비교 함수 |
| `main.py` | REPL 루프, 명령어 파싱(`shlex`), `short_hash`/`resolve_hash`(40자리↔4자리 변환), 명령어 라우팅 테이블. `LOG`/`ANCESTORS`는 전체 40자리, 그 외는 4자리로 출력 |

**설계 결정 하나 짚어두면**: `Commit`은 해시맵 체이닝용 포인터(`hash_next`)를 직접 갖지 않는다. Mini Redis 프로젝트에서는 Entry가 해시맵+LRU 두 자료구조에서 동시에 쓰여 포인터 공유가 효율적이었지만, Mini Git은 Commit이 해시맵 한 곳에서만 저장 목적으로 쓰이므로 그 이점이 없다. 대신 `hashmap.py`에 별도 `Node` 래퍼를 둬서 `Commit`은 순수 도메인 데이터로, 체이닝 책임은 `Node`로 분리했다.

## 4. 명령어 정리 및 로직

| 명령어 | 문법 | 로직 |
|---|---|---|
| `INIT` | `init <user_name>` | 이미 초기화된 저장소(head가 설정됨)면 branches/head는 보존하고 current_user만 갱신. 처음이면 `main` 브랜치 생성 |
| `BRANCH` | `branch <name>` | 현재 HEAD가 가리키는 커밋이 존재하면 새 브랜치 생성. 없으면 `Cannot create branch before the current branch has a commit`. 이미 있는 이름이면 `Branch already exists: <name>` |
| `SWITCH` | `switch <name>` | HEAD를 지정 브랜치로 이동. 없는 브랜치면 `Unknown branch: <name>` |
| `COMMIT` | `commit "<msg>"` | 현재 HEAD 커밋을 parent로 새 Commit 생성(40자리 hash) → hashmap 저장 → 역색인 갱신 → 브랜치 갱신 |
| `LOG` | `log` | DFS로 부모 우선 출력(위상 정렬). 브랜치별로 리프에서 시작해 조상을 통째로 끌어와 브랜치끼리 섞이지 않게 그룹핑 |
| `LOG --sort-by` | `log --sort-by=date\|author` | 병합 정렬로 전체 커밋 정렬 (위상 순서 대신 값 기준, 브랜치 그룹핑 없음). 그 외 값은 `Invalid args` |
| `PATH` | `path <hash1> <hash2>` | 입력받은 짧은 hash를 `resolve_hash`로 전체 hash로 변환 후 무방향 BFS 최단 경로. 여러 개면 사전순 최소, 없으면 `No path` |
| `ANCESTORS` | `ancestors <hash>` | 짧은 hash를 전체로 변환 후 BFS로 도달 가능한 모든 조상 hash 수집, 정렬 출력 |
| `SEARCH` | `search <keyword>` 또는 `search --author=<name>` | 역색인 조회 |

**공통 규칙**: 명령어 대소문자 무시, 따옴표 포함 인자는 `shlex.split`으로 파싱, `EXIT`/`QUIT`로 종료. 인자 오류는 `Invalid args`, 없는 브랜치는 `Unknown branch: <name>`, 없는 커밋(짧은 hash로 못 찾음)은 `Unknown commit: <입력값>`, 짧은 hash가 여러 커밋에 매칭되면 `Ambiguous commit: <입력값> matches N commits`.

**`LOG`/`ANCESTORS` 출력 포맷**: 실제 `git log`(옵션 없는 기본 형태)와 동일한 여러 줄 형식을 쓴다. hash는 40자리 전체를 그대로 표시한다(실제 `git log` 기본형과 동일; 짧은 hash는 `COMMIT` 확인 메시지·`PATH`·`SEARCH`에서만 쓴다, 2-2절 참고).
```
commit <40자리 전체 hash> (HEAD -> <현재 브랜치>, <다른 브랜치>...)
Author: <작성자>
Date:   <YYYY-MM-DD HH:MM:SS>

    <커밋 메시지>
```
브랜치 표시는 그 커밋을 tip으로 가리키는 브랜치에만 붙는다. 현재 HEAD가 위치한 브랜치는 `HEAD -> `를 붙이고, 그 외 브랜치는 이름만 표시한다. 태그가 없는 커밋(과거 커밋, 여러 브랜치의 공유 조상 등)은 `commit <hash>` 한 줄로만 표시된다.

## 5. 추가 학습 및 한계

- **find_by_prefix의 예외 케이스**: 접두사가 2자리 미만이면 버킷을 하나로 특정할 수 없어(예: 1자리 `"7"`은 버킷 `0x70`~`0x7F` 16개에 걸쳐있음) 전체 버킷을 순회하는 예비 경로로 처리한다. 16진수가 아닌 문자가 섞인 접두사(`int(key[:2], 16)` 실패)는 `ValueError`를 잡아 빈 리스트(= `Unknown commit`)로 처리한다.
- **짧은 hash 충돌은 저장 시점이 아니라 조회 시점에 처리**: 40자리 전체가 겹칠 확률은 무시 가능한 수준이라 저장 단계에서는 아무 조치가 없다. 반면 4자리 접두사는 커밋이 많아지면 여러 개가 매칭될 수 있는데(생일 문제), 이 경우 자동으로 회피하지 않고 `Ambiguous commit` 에러로 사용자에게 알려 더 긴 접두사를 입력하도록 한다 — 실제 `git show`가 모호한 짧은 SHA를 만났을 때와 동일한 처리 방식이다.
- **대규모 확장 시 병목 예측**: 현재 해시맵은 버킷 개수(256)가 고정이며 리해시(rehash)를 구현하지 않았다. load factor(`n/256`)가 임계값(0.75)을 넘는 시점은 `n > 192`, 즉 커밋 200개에 근접할 때부터 이론상 리해시가 필요한 시점으로 예측된다. 세션당 커밋 수십 개 규모라 실질적 성능 저하는 미미하다. 참고로 실제 Git도 커밋이 매우 많이 쌓이면 loose object 방식 대신 packfile(정렬된 인덱스 + 이진 탐색)로 전환하는데, 이는 리해시가 아니라 완전히 다른 저장 전략으로의 전환이다.
- **해시 재현성**: `timestamp`가 hash 계산에 포함되어 있어, 동일한 message/author/parents로 커밋을 여러 번 만들어도 매번 다른 hash가 나온다. 이는 의도된 설계로, 완전히 동일한 내용의 커밋이 hash 충돌 없이 별개로 기록될 수 있게 한다. 다만 이 때문에 동일 입력에 대한 결정론적 테스트(같은 시나리오 재실행 시 같은 hash 기대)는 불가능하며, 현재는 별도 테스트 파일 없이 REPL 시나리오로 구조적 성질을 확인한다.
- **동률 처리**: `LOG --sort-by`에서 값이 같은 커밋들은 병합 정렬의 안정성 덕분에 정렬 전 원본 순서(=`get_all_commits()`가 반환하는 해시맵 내부 순회 순서, 커밋 생성 시간과는 무관)가 그대로 유지된다.
- **INIT 재호출 방어**: `INIT`을 다시 호출해도 이미 초기화된 상태(head가 설정됨)라면 `branches`/`head`를 보존하고 `current_user`만 갱신한다 — 실제 `git init`이 기존 저장소를 다시 초기화해도 커밋/브랜치를 지우지 않는 것과 동일한 원칙. (상세 경위는 7번 트러블슈팅 참고)

## 7. 트러블슈팅 (설계 변경 이력)

### 7-1. 카운터 → SHA-1

처음엔 hash 생성 방식으로 카운터 기반(구조적으로 충돌 불가능)도 검토했으나, Content-Addressable Storage라는 Git의 핵심 철학을 직접 체감하기 위해 SHA-1을 선택했다(2-1절).

### 7-2. [폐기됨] "4자리로 저장" + `extend_hash` 자동 확장

**당시 결정**: 세션당 커밋이 수십 개 수준인 프로젝트 규모를 고려해, hash를 처음부터 4자리로 잘라서 **저장 키 자체**로 사용하기로 했다. 생일 문제 근사식(`1 - e^(-n²/2m)`)으로 계산한 결과, 4자리(16⁴=65,536개 공간) 기준 커밋 30개에서 충돌 확률 0.68% 수준이라 실용적으로 안전하다고 판단했다.

**충돌 대응**: 확률이 낮아도 0이 아니므로, `Commit`이 SHA-1 전체 결과(40자리, `full_hash`)를 별도로 보관하고 `hash_length`(초기 4)만큼 잘라 쓰다가, `HashMap.put()`에서 삽입 전 동일 hash 존재 여부를 확인해 충돌 시 `hash_length`를 1씩 늘려 재계산 없이 더 긴 접두사를 쓰는 `extend_hash()`를 구현했다.

**폐기 이유**: 실제 Git은 40자리를 항상 저장하고, 표시에만 짧은 hash(보통 7자리, 저장소 크기에 따라 자동 조정)를 쓴다는 점을 다시 짚어보면서, "저장 자체를 4자리로 줄이고 충돌 시 강제로 늘리는" 접근이 실제 Git 구조와 근본적으로 다르다는 결론에 이르렀다. 저장은 항상 40자리로 통일하고, 4자리는 순수하게 조회 편의를 위한 별명으로만 쓰는 현재 구조(2-2절)로 전면 재설계했다. 이 과정에서 `full_hash`/`hash_length`/`extend_hash()`가 모두 삭제되고, 대신 `HashMap.find_by_prefix()` + `main.py`의 `resolve_hash()`가 추가됐다.

### 7-3. [폐기됨] djb2 해시 함수

**당시 결정**: `HashMap._hash_index()`는 Mini Redis 프로젝트에서 쓴 djb2 스타일 해시 함수(문자열을 33배씩 누적)를 그대로 재사용해 버킷 인덱스를 계산했다.

**폐기 이유**: hash를 40자리 저장으로 재설계하면서 짧은 접두사 조회(`find_by_prefix`)가 버킷 전체(16개)를 매번 순회해야 하는 문제가 생겼다. djb2는 "입력이 임의의 문자열이라 값이 골고루 안 흩어질 수 있다"는 가정 하에 필요한 믹싱 함수인데, 여기 들어오는 key는 이미 SHA-1이 계산한 균등분포 값이라 추가로 섞을 필요가 없다는 걸 깨달았다. 그래서 key의 앞 2자를 그대로 버킷 번호로 쓰는 방식(256버킷)으로 교체했다(2-3절). 이는 실제 Git의 loose object 디렉토리 샤딩(`.git/objects/xx/`)과 동일한 발상이며, 부수 효과로 `find_by_prefix()`가 버킷 전체 순회 없이 해당 버킷 하나만 확인하면 되도록 빨라졌다.

### 7-4. INIT 재호출 시 유령 커밋

**발견 경위**: `INIT`을 두 번째 호출하면 `branches` 딕셔너리를 통째로 새로 만드는 구현 때문에, 기존 브랜치가 가리키던 커밋들이 hashmap에는 남아있지만 어느 브랜치도 가리키지 않는 상태(유령 커밋, dangling commit)가 되는 문제를 발견했다.

**수정**: 실제 `git init`은 이미 존재하는 저장소에서 다시 실행해도 커밋/브랜치를 지우지 않는다는 점에 착안해, `Repository.init()`을 "이미 초기화된 상태(head가 설정됨)라면 branches/head는 보존하고 current_user만 갱신"하도록 수정했다.

### 7-5. BRANCH 이름 중복 시 몰래 덮어쓰기

**발견 경위**: 이미 존재하는 브랜치 이름으로 `BRANCH`를 실행하면, 에러 없이 조용히 그 브랜치를 현재 HEAD 위치로 덮어써버리는 문제를 발견했다. 예를 들어 `feature`에 있는 상태에서 `branch main`을 실행하면 `main`이 `feature`의 최신 위치로 몰래 옮겨져, 원래 `main`이 가리키던 커밋이 태그를 잃어버렸다.

**수정**: 실제 Git이 `git branch <existing-name>`에 `fatal: A branch named '<name>' already exists`로 거부하는 것과 동일하게, `main.py`의 `handle_branch()`에 이름 중복 검사를 추가해 `Branch already exists: <name>`으로 거부하도록 했다.

### 7-6. [폐기됨] LOG 형제 순서를 날짜로 tie-break

**당시 결정**: `LOG`에서 형제 브랜치끼리의 상대 순서가 해시맵 순회 순서(사실상 무작위)로 결정되는 게 불안정하다고 판단해, 바깥 순회 순서를 `sort_by_date()`로 정렬한 뒤 위상정렬 DFS를 돌리는 방식을 시도했다.

**폐기 이유**: 이 시스템은 자식 커밋을 만들려면 부모의 hash가 먼저 존재해야 하므로, "부모의 timestamp가 항상 자식보다 이르다"는 인과관계가 구조적으로 항상 성립한다. 이 때문에 순수하게 timestamp로만 정렬해도 위상정렬 조건(부모가 자식보다 먼저)이 저절로 만족되는 것을 실험으로 확인했다 — 즉 "형제를 날짜로 tie-break"한 결과가 `LOG --sort-by=date`와 수학적으로 항상 동일해져, 두 명령어가 사실상 중복이 되는 문제를 발견했다. 대신 리프(다른 커밋의 부모로 참조되지 않는 커밋, 즉 브랜치 tip)를 찾아 날짜순으로 정렬하고, 각 리프에서 시작해 그 브랜치의 조상 전체를 한 번에 끌어오는 방식(2-4절)으로 재설계했다. 이 방식은 브랜치 줄기가 서로 안 섞이게 유지되어 `--sort-by=date`(커밋 단위로 뒤섞임)와 명확히 구분되는 결과를 낸다.

### 7-7. LOG/ANCESTORS 출력 포맷 — 여러 차례 조정 끝에 실제 git log 스타일로 확정

**과정**: 브랜치 태그 표시 방식을 두고 세 단계를 거쳤다.
1. 처음엔 tip 커밋에만 브랜치 이름을 표시했는데, 브랜치가 갈라지는 공통 조상 커밋에는 태그가 전혀 안 붙어 "소속 불명"처럼 보이는 문제를 발견했다.
2. 이를 해결하려고 각 커밋이 어느 브랜치들의 조상인지 `ancestors()`로 매번 계산해 전부 표시하는 방식을 시도했으나, 브랜치가 많아지면 태그가 길어지고 계산 비용도 늘어나며, 무엇보다 실제 Git이 tip에만 브랜치 라벨을 붙이는 방식과 다르다는 점, 그리고 프로젝트 스펙의 결과 예시 자체도 단순한 tip 표시 수준이라는 점을 다시 확인해 폐기했다.
3. 최종적으로 tip 전용 표시로 되돌리되, 출력 포맷 자체를 실제 `git log`(옵션 없는 기본 형태)와 동일한 여러 줄 구조(`commit <hash> (HEAD -> branch, ...)` / `Author:` / `Date:` / 들여쓴 메시지)로 바꿨다. 현재 HEAD가 위치한 브랜치는 `HEAD -> `를 붙여 실제 git과 동일하게 구분했다(4절 참고).
4. 처음엔 `commit` 줄에도 짧은 4자리 hash를 썼는데, 실제 `git log`(옵션 없는 기본형)는 4/7자리로 축약하지 않고 **40자리 전체**를 그대로 보여준다는 점을 다시 확인해, `LOG`/`ANCESTORS`만 전체 40자리로 바꿨다. `COMMIT` 확인 메시지·`PATH`·`SEARCH`는 실제 Git도 짧은 hash를 쓰는 맥락(커밋 요약 줄 등)이라 4자리를 그대로 유지했다. hash가 몇 자리로 보이든 `resolve_hash()`가 접두사 매칭으로 처리하므로, 화면에 40자리가 찍혀 있어도 그 앞 4자리만 복사해 다른 명령어에 입력해도 정상 동작한다.
