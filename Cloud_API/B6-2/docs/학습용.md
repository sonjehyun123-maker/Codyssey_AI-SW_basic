# HTTP → API → REST → SDK 완전 정리

이 문서는 "Git 커밋/PR 메시지 자동 생성기" 프로젝트를 만들면서
"왜 이렇게 짜는지"를 밑바닥부터 이해하기 위해 정리한 학습 노트입니다.

---

## 전체 그림 한눈에

```
HTTP                 →  클라이언트-서버가 대화할 때 쓰는 공통 언어 (모두가 씀)
  └─ REST            →  API를 잘 설계하기 위한 스타일 가이드
       └─ API        →  특정 서비스(Gemini)가 정해둔 "이렇게 요청하면 이렇게 응답한다"는 메뉴판
            └─ SDK   →  그 메뉴판을 편하게 쓰라고 포장해둔 라이브러리
```

---

## 1. 클라이언트-서버

- **클라이언트** = 요청하는 쪽 (재현님의 파이썬 코드, 브라우저)
- **서버** = 요청을 처리해서 응답하는 쪽 (Gemini API 서버, 유튜브 서버)

**비유:** 손님(클라이언트)이 주문하면 → 주방(서버)이 요리해서 내줌

| 예시 | 클라이언트 | 서버 |s
|---|---|---|
| 유튜브 시청 | 크롬 브라우저 | 유튜브 서버 |
| 이 프로젝트 | `python main.py commit` 실행 중인 내 PC | Gemini API 서버 |

---

## 2. HTTP — 요청과 응답의 형식

**HTTP = 클라이언트와 서버가 대화할 때 쓰는 공통 규약**

### 요청 (Request) — 4가지 구성요소

| 요소 | 역할 | 이 프로젝트 코드 예시 |
|---|---|---|
| URL | 어디로 보낼지 (주소) | `generativelanguage.googleapis.com/...` |
| 메서드 | 뭘 하고 싶은지 | `POST` |
| 헤더 | 부가 정보 (인증 등) | `x-goog-api-key: ...` |
| 본문(Body) | 실제로 보낼 내용 | `{"contents": [...]}` (JSON) |

**메서드 종류**
- **GET** — 조회만 (아무것도 안 보냄) → 예: GitHub 프로필 정보만 조회
- **POST** — 데이터를 실어서 보내 처리 요청 → 예: diff를 보내서 커밋 메시지 생성 요청

### 응답 (Response) — 2가지 핵심

| 요소 | 역할 |
|---|---|
| 상태 코드 | 성공/실패를 숫자로 알려줌 |
| 본문(Body) | 실제 결과 데이터 |

**상태 코드 카테고리**
- **2xx** — 성공 (`200 OK`)
- **4xx** — 클라이언트가 잘못 보냄 (`403 Forbidden` = 인증 실패, `404 Not Found` = 잘못된 URL)
- **5xx** — 서버 쪽 문제 (`500 Internal Server Error`)

> 코드의 `response.raise_for_status()`가 하는 일 — 상태 코드가 4xx/5xx면 자동으로 에러를 발생시켜 `except`로 잡히게 함

### 한 문장 요약

> **HTTP = "요청 4가지(URL/메서드/헤더/본문)를 보내면, 응답 2가지(상태코드/본문)로 돌아오는 대화 규칙"**

---

## 3. API — 서비스별 메뉴판

**API (Application Programming Interface) = 두 프로그램이 소통할 때 쓰는 정해진 규칙**

- HTTP가 "우편 시스템 자체(주소 쓰는 법, 봉투 형식)"라면
- API는 "특정 회사가 정한 자기들만의 규칙" (사이트마다 다름)

**비유:** 손님은 주방 내부를 몰라도 됨. 메뉴판만 보고 "이 이름으로, 이 재료 조합으로 주문하면 이 요리가 나온다"만 알면 됨.

Gemini API의 "메뉴판" 규칙 예시:
> `generateContent`라는 이름으로 POST 요청을 보내면서, body에 `contents` 키로 텍스트를 넣으면, AI가 생성한 텍스트를 응답으로 준다.

### body 안 옵션 값들 (temperature, maxOutputTokens)

떡볶이 주문 비유:
- `contents` (프롬프트) = 메인 메뉴 (떡볶이)
- `temperature` = 맛 강도/스타일 조절 (낮으면 담백하고 일관된 맛, 높으면 로제·마라처럼 창의적인 맛)
- `maxOutputTokens` = 양 조절 (적게/많이)

---

## 4. REST — API를 잘 설계하는 스타일 가이드

API를 아무렇게나 설계하면 사이트마다 완전히 달라져서 배우기 어려움 → 그래서 생긴 공통 스타일이 **REST**입니다.

REST 스타일의 핵심 규칙 예시:
> "조회는 GET, 새로 만들거나 처리 요청은 POST를 쓰자"

Gemini API도 REST 스타일을 따르기 때문에, "생성해달라"는 요청에 자연스럽게 `POST`를 쓴 것이 REST 관례와 맞아떨어짐.

### 이 과제가 "REST 방식으로 직접 연동"을 요구한 이유

| 방식 | 특징 |
|---|---|
| SDK 사용 | `model.generate_content(prompt)` 한 줄로 끝 → 편하지만 URL/헤더/상태코드가 전부 라이브러리 뒤에 숨음 |
| REST 직접 호출 | 헤더/본문/에러처리를 직접 조립해야 함 → 불편하지만 HTTP/API 원리가 몸에 남음, 어떤 API든 재사용 가능한 범용 스킬이 됨 |

과제가 REST 직접 호출을 요구한 이유는, SDK 뒤에 숨기지 않고 HTTP 원리를 직접 다루는 경험을 시키기 위함입니다.

---

## 5. SDK — 메뉴판을 편하게 쓰라고 포장해둔 도구

**SDK (Software Development Kit) = 특정 서비스를 더 쉽게 쓰라고 그 회사가 미리 만들어둔 라이브러리**

### REST 직접 호출 vs SDK 비교

**REST 직접 호출 (이 프로젝트 방식)**
```python
headers = {"x-goog-api-key": api_key}
body = {"contents": [{"parts": [{"text": prompt}]}]}
response = requests.post(url, headers=headers, json=body)
data = response.json()
result = data["candidates"][0]["content"]["parts"][0]["text"]
```

**SDK 사용 시**
```python
import google.generativeai as genai
genai.configure(api_key=api_key)
model = genai.GenerativeModel("gemini-3.5-flash")
result = model.generate_content(prompt).text
```

**비유:** REST 직접 호출 = 시장에서 재료 사서 직접 요리, SDK = 밀키트 (넣고 버튼만 누르면 끝)

---

## 6. 최종 코드 전체 매핑

```python
response = requests.post(                          # 메서드: POST (REST 관례)
    url,                                            # URL (API가 정한 주소)
    headers={"x-goog-api-key": api_key},            # 헤더 (API가 요구하는 인증 방식)
    json=body                                       # 본문 (API가 정한 요청 형식)
)
response.raise_for_status()                         # 상태코드 확인 (HTTP 규칙)
data = response.json()                              # 응답 본문 파싱 (HTTP 규칙)
```

이 5줄에 HTTP(URL/메서드/헤더/본문/상태코드) + API(Gemini만의 요청 형식) + REST(POST를 쓰는 이유)가
전부 응축되어 있습니다. SDK를 썼다면 이 5줄이 함수 한 줄 뒤로 완전히 숨었을 내용입니다.
