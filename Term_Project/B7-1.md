# 코딩 학습 Q&A 챗봇

FastAPI 기반 팀 프로젝트(120시간, 4인 팀)로, 코디세이 공개 API(OpenAI 호환)를
통해 CS 개념·코드 질문에 답하는 코딩 학습 튜터 챗봇을 기획부터 배포까지
직접 진행했습니다.

## 프로젝트 개요

- **문제 정의**: 컴공/부트캠프 학생이 코드 에러나 CS 개념 질문에 즉시 답을
  얻을 곳이 마땅치 않다는 문제에서 출발했습니다.
- **핵심 시나리오**: 로그인한 사용자가 질문을 입력하면 AI가 답변하고, 이전
  대화 문맥(최근 5턴)을 반영해 후속 질문에도 자연스럽게 이어서 답합니다.
- **기술 스택**: FastAPI, Jinja2(서버 템플릿), PostgreSQL(SQLAlchemy),
  Vercel(서버리스 배포), 코디세이 공개 API(OpenAI 호환)
- **인증**: JWT + HttpOnly 쿠키

### 팀 구성 (4계층 구조)

| 계층 | 담당 | 역할 |
|---|---|---|
| Auth — 서비스의 문 | A | 회원가입/로그인, 접근 제어, 저장소·CI 세팅 |
| **Core — 서비스의 심장** | **B (본인)** | **챗봇·AI 연동** |
| Data — 서비스의 기억 | C | DB 스키마, 대화 로그 저장/조회 |
| Ops — 서비스의 땅 | D | 배포, CI/CD, 환경변수 관리 |

각 계층은 정해진 파일 경계를 지킵니다. 라우터는 요청 검증만 하고 SQL이나
AI SDK를 직접 호출하지 않으며, 서비스 계층은 HTTP를 다루지 않고, 모든 DB
접근은 `crud.py` 하나를 거칩니다. 덕분에 서로 다른 계층을 동시에 작업해도
충돌이 크지 않았습니다.

### 고민했던 부분

**1. AI 프로바이더를 뭘로 정할지**

처음엔 "코딩 벤치마크 성능이 가장 좋은 쪽"을 근거로 삼으려 했지만, 실제로
찾아보니 미니급 모델 체급에서는 Claude Haiku 4.5가 GPT 미니급보다 오히려
근소하게 앞서는 지표도 있었습니다. 성능 우위를 근거로 내세우기엔 데이터가
뒷받침해주지 않는다는 걸 깨닫고, 판단 기준을 바꿨습니다.

콘솔에서 확인해보니 3사 미니급 모델의 차감 배수가 전부 0.5로 동일했고,
코디세이 매뉴얼의 두 규격(OpenAI/Anthropic) 스펙을 비교해보니 Anthropic은
`max_tokens`가 필수라 빠뜨리면 요청이 실패하고 별도 헤더도 매번 챙겨야
한다는 차이를 발견했습니다. 성능·비용이 근소한 차이라면, 제한된 개발
기간(120시간) 안에서 연동 실수 위험이 적은 쪽을 택하는 게 합리적이라
판단해 OpenAI로 정했습니다.

**2. 모델명이 실제로 존재하지 않았던 문제**

처음엔 관성적으로 `gpt-4o-mini`를 상수에 넣어뒀는데, 실제 코디세이 콘솔의
모델 목록을 확인해보니 그 모델 자체가 제공되지 않는다는 걸 뒤늦게
발견했습니다. 실제 사용 가능한 모델(`gpt-5-mini`, `gpt-5.4-mini`,
`gpt-5.4`, `gpt-5.5`) 중 최신 미니급인 `gpt-5.4-mini`로 정정했습니다. 이
경험으로 설정값을 코드에 넣기 전에 실제 제공 목록을 먼저 확인하는 습관이
생겼습니다.

**3. `AI_MODEL`을 상수로 둘지 환경변수로 둘지**

재배포 없이 바꿀 수 있다는 유연성(환경변수) vs. Git 히스토리로 변경
이력이 남는 안정성(상수) 사이에서 고민했습니다. 여러 모델을 실험할
계획이 없고 하나로 고정해서 쓸 예정이라 상수로 결정했습니다. 반대로
`AI_TIMEOUT_SECONDS`는 시연 중 일부러 0.1초로 낮춰 실패 경로를 보여줘야
해서 환경변수로 남겨, 같은 종류의 설정값도 용도에 따라 다르게
처리했습니다.

**4. 재시도 대상 구분**

모든 실패를 동일하게 재시도하지 않고, 예외 종류에 따라 다르게 처리했습니다.
타임아웃·일시적 API 오류는 1회 재시도하되, 이미 한도 초과인 `RateLimitError`는
재시도해도 다시 걸릴 가능성이 높아 즉시 실패 처리했습니다.

### 구현 내용

오류는 상태코드·문구를 직접 고르지 않고, 공용 `ErrorCode`
(`AI_TIMEOUT` / `RATE_LIMITED` / `AI_ERROR` / `AI_UNKNOWN`)로만 매핑해
`AppError`를 발생시킵니다. 상태코드·응답 형식 변환은 전역 예외 핸들러가
전담합니다.

```python
# 타임아웃 → raise AppError(ErrorCode.AI_TIMEOUT)   (1회 재시도 후)
# 429      → raise AppError(ErrorCode.RATE_LIMITED)  (즉시)
# 그 외    → raise AppError(ErrorCode.AI_ERROR / AI_UNKNOWN)
```

- 타임아웃 10초, 재시도 1회
- `request_id`는 전역 미들웨어가 발급·전파해 별도로 인자로 넘기지 않음
- 시스템 프롬프트로 코딩 학습 튜터 페르소나 부여, 한국어 답변 고정
