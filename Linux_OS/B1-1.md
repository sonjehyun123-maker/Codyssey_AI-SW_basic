# 시스템 관제 자동화 스크립트 개발
## 미션 소개
> **"로그가 없는 서버 장애 복구는 '감'에 의존하게 되며, 이는 장애 반복의 원인이 됩니다."**
> 리눅스는 현대 서버 환경의 표준입니다. 
* 다중 사용자 권한 관리
* 네트워크 보안
* 시스템 리소스 관제 및 로그 자동화
* 쉘 스크립트를 설계 및 구축
> 최종적으로 애플리케이션 배포 환경 안정화 및 시스템 상태를 데이터로 기록·관제할 수 있는 백엔드 엔지니어링 역량을 확보
### 미션 목적
 * "지속적으로 살아 움직이는 Runtime System" 구현
### - process lifecycle
* "프로세스가 어떻게 생성되고, 유지되고, 종료되는가"
     * 예시)위 과정은 아래 과정을 압축한 것.
    ```bash
    python3 agent_app.py
    ```
    ```bash
    → fork()
    → execve()
    → python process 생성
    → socket bind
    → listen
    → running
    → signal handling
    → terminate
    ```
* 프로그램이 죽지않고 살아남는가가 중요!!
    * RUN 보다 SURVIVE가 핵심
    * 예시 트러블 시나리오
    ```code
    메모리 계속 쌓임
        ↓
    OS가 강제로 프로세스 죽임 (OOM Kill)
        ↓
    서비스 갑자기 다운
        ↓
    로그도 없음
        ↓
    "왜 죽었지?" → 원인 모름 😱
    ```
    * 이럴 때 **lifecycle** 추적!
        * 언제 죽는가
        * 죽으면 누가 감지하는가
        * 재시작 가능한가

### - daemon orchestration
* "백그라운드에서 돌아가는 서비스들을 관리하는 관리자"
* 핵심: systemd
    ```
    운영서버 = 혼자 수십개 서비스 켜고 끄고 감시
    → 사람이 직접 못함
    → systemd가 자동으로 관리
    ```
* 큰 그림                           ← 이 부분 추가 추천
    ```
    systemd     → 서버 1대 관리
    Kubernetes  → 서버 수백대 관리
    ```
    * K8s(Kubernetes)는 systemd 개념을 클러스터로 확장한 것

### - permission enforcement
* "프로세스가 자원에 접근할 때 권한을 검사하는 과정"
    * 접근 검사 순서 (위에서 아래로 순차 검사)
    ```
    1. UID        # 이 유저가 누구인가
    2. GID        # 어느 그룹에 속하는가
    3. ACL        # 특정 유저에게만 예외 권한 부여
    4. Capability # root 권한을 기능별로 쪼갠 세분화 권한
    ```
    * 핵심 원칙: 최소 권한만 부여 (필요한 것만 딱 허용)
### - runtime configuration
* 실행 환경과 코드 분리
    * 하드코딩할 경우:
        환경 변경 시 코드 수정 → 재빌드 → 재배포 → 위험 증가

    * 환경변수/설정파일로 분리할 경우:
        코드 변경 없이 설정값만 변경 → 재배포 없이 환경 전환 가능
* 대표적인 분리 방법
    * 환경변수     (DB_HOST, PORT, API_KEY)
    * 설정파일     (.env, config.yaml)
    * 시크릿 관리  (Vault, AWS Secrets Manager)

* 핵심 원칙
    * 코드는 동일하게 유지
    * dev / staging / production 환경을 설정값으로만 구분
### - operational observability
* "실행 중인 서버/프로세스의 내부 상태를 외부에서 파악하는 것"
    * 왜 필요한가?
        * 서버는 블랙박스 → 내부에서 무슨 일이 일어나는지 모름
        * 문제 발생 후 원인 추적 가능

    * 3가지 핵심 수단
        ```
        Logs    # 무슨 일이 일어났는가       (이벤트 기록)
        Metrics # 얼마나 나쁜가            (CPU, 메모리 수치)
        Traces  # 어디서 터졌는가           (요청 흐름 추적)
        ```

    * 연결 고리 (앞서 배운 내용과 연결)
        ```
        OOM Kill로 프로세스 죽음
            → Log 없으면 원인 모름
            → Observability 있으면 추적 가능
        ```

## [Step 1] OrbStack 기반 Linux 운영 환경 설정
### 1-1. 환경 구성 
```bash
macOS
└── OrbStack
    └── Ubuntu 22.04 Linux VM
```
### 1-2. OrbStack 선택 이유
| 요소 | 이유 |
|---|---|
| Linux Kernel 환경 |	Ubuntu 운영 기능 재현 가능 | 
| Port Forwarding	| SSH/APP 포트 테스트 쉬움 |
| Filesystem 접근 |	로그 확인 편리 |
| Resource Isolation |	VM처럼 독립 동작 |
| Lightweight |	Docker Desktop보다 가벼움 |
