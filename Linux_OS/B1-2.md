> **"로그 없는 재부팅은 원인을 묻히게 만들고, 동일한 실서버 장애를 반복시킬 뿐입니다."**
* 개발자가 작성한 코드는 운영체제 위에서 '프로세스' 형태로 실행됩니다. 
* 본 미션에서는 실서버 환경에서 치명적인 시스템 장애(Memory Leak/OOM, CPU Spike, Deadlock)가 발생했을 때, 단순 현상 파악을 넘어 관제 데이터와 로그를 근거로 원인을 추론하는 훈련을 합니다.
* 최종적으로 현업 개발자처럼 문제를 진단하고 GitHub Issue 형태의 기술 리포트로 기록·공유할 수 있는 실전 트러블슈팅 및 협업 커뮤니케이션 역량을 강화합니다.

# [Bug] OOM Crash - MemoryGuard 정책에 의한 프로세스 강제 종료

## 1. Description (현상 설명)

`agent-app-leak` 실행 후 시간이 지남에 따라 메모리 사용량이 지속적으로 증가하였고,
최종적으로 `SELF-TERMINATED (Memory Limit Exceeded)` 메시지와 함께 프로세스가 종료되었습니다.

해당 현상은 MEMORY_LIMIT 값이 낮을수록 더 빠르게 발생했습니다.

---

## 2. Evidence & Logs (증거 자료)

### monitor.sh 결과

```text
[2026-05-20 04:55:58] PID:2818 CPU:3.6% MEM:0.0%
[2026-05-20 04:56:10] PID:2818 CPU:0.4% MEM:0.0%
[2026-05-20 04:56:20] PID:2818 CPU:0.2% MEM:0.0%
```

CPU 사용률은 낮고 안정적이었으나,
애플리케이션 내부 Heap 사용량은 지속적으로 증가했습니다.

### 프로그램 실행 로그

```text
2026-05-20 04:55:58 [INFO] [MemoryWorker] Current Heap: 25MB
2026-05-20 04:56:01 [INFO] [MemoryWorker] Current Heap: 50MB
2026-05-20 04:56:04 [INFO] [MemoryWorker] Current Heap: 75MB
...
2026-05-20 04:56:28 [INFO] [MemoryWorker] Current Heap: 275MB

[CRITICAL] [MemoryGuard] Memory limit exceeded (275MB >= 256MB)
[CRITICAL] [MemoryGuard] Self-terminating process 2819 to prevent system instability.

>>> [SYSTEM] SELF-TERMINATED (Memory Limit Exceeded) <<<
```

---

## 3. Root Cause Analysis (원인 분석)

애플리케이션 내부 `MemoryWorker`가 Heap 메모리를 지속적으로 증가시키고 있으며,
메모리 해제(free/garbage collection)가 수행되지 않는 것으로 보입니다.

이로 인해 Heap 사용량이 선형적으로 증가하는 Memory Leak 현상이 발생했습니다.

프로세스 메모리 사용량이 `MEMORY_LIMIT` 환경변수 임계치를 초과하자,
애플리케이션 내부 보호 정책인 `MemoryGuard`가 시스템 불안정을 방지하기 위해
프로세스를 Self-Termination 처리했습니다.

---

## 4. Workaround & Verification (조치 및 검증)

### 조치 내용

`MEMORY_LIMIT` 값을 `128MB → 256MB`로 증가시켰습니다.

### Before

- MEMORY_LIMIT=128
- 약 15초 내 종료

### After

- MEMORY_LIMIT=256
- 약 30초 이상 생존

### 검증 결과

메모리 제한 증가 이후 프로세스 생존 시간이 증가함을 확인했습니다.

다만 이는 임시 조치이며,
근본적인 해결을 위해서는 `MemoryWorker` 내부 메모리 해제 로직 개선이 필요합니다.

# [Bug] Deadlock - 멀티스레드 환경에서 교착상태 발생으로 프로세스 무응답

## 1. Description (현상 설명)

`agent-app-leak` 실행 후 프로세스가 종료되지 않은 상태로 유지되었으나,
CPU 사용률과 로그 출력이 모두 멈춘 무응답 상태가 발생했습니다.

프로세스 PID는 유지되었지만,
Worker Thread 간 자원 점유 상태로 인해 작업이 더 이상 진행되지 않았습니다.

---

## 2. Evidence & Logs (증거 자료)

### 프로그램 실행 로그

```text
2026-05-20 05:02:57 [INFO] [Worker-Thread-1] LOCK ACQUIRED: [Shared_Memory_A]
2026-05-20 05:02:57 [INFO] [Worker-Thread-2] LOCK ACQUIRED: [Socket_Pool_B]

2026-05-20 05:02:59 [INFO] [Worker-Thread-1] Need resource [Socket_Pool_B] to finish job.
2026-05-20 05:02:59 [INFO] [Worker-Thread-2] Need resource [Shared_Memory_A] to write logs.

2026-05-20 05:02:59 [INFO] [Worker-Thread-1] WAITING for [Socket_Pool_B]... (Status: BLOCKED)
2026-05-20 05:02:59 [INFO] [Worker-Thread-2] WAITING for [Shared_Memory_A]... (Status: BLOCKED)
```

### top 결과

```text
%Cpu(s): 100.0 id

PID   COMMAND           %CPU
3279  agent-app-leak     0.0
3280  agent-app-leak     0.0
```

프로세스는 살아있으나 CPU 사용률이 거의 0% 상태로 유지되었고,
추가 로그도 더 이상 출력되지 않았습니다.

---

## 3. Root Cause Analysis (원인 분석)

멀티스레드 환경에서 두 Worker Thread가 서로 다른 Lock을 선점한 상태에서,
상대방이 점유 중인 자원을 추가로 요청하면서 교착상태(Deadlock)가 발생했습니다.

### Deadlock 흐름

- Worker-Thread-1
  - Shared_Memory_A Lock 획득
  - Socket_Pool_B 요청 후 대기

- Worker-Thread-2
  - Socket_Pool_B Lock 획득
  - Shared_Memory_A 요청 후 대기

결과적으로 두 스레드는 서로 상대 자원을 기다리는 순환 대기(Circular Wait) 상태에 진입했고,
어느 스레드도 Lock을 해제하지 못해 프로그램 전체가 무응답 상태가 되었습니다.

이는 Deadlock 4대 조건 중 다음이 모두 충족된 사례입니다.

- Mutual Exclusion
- Hold and Wait
- No Preemption
- Circular Wait

---

## 4. Workaround & Verification (조치 및 검증)

### 조치 내용

`MULTI_THREAD_ENABLE=true` 환경을 비활성화하여 단일 스레드 모드로 실행했습니다.

### Before

- MULTI_THREAD_ENABLE=true
- Deadlock 발생
- 로그 출력 중단
- 프로세스 무응답 상태

### After

- MULTI_THREAD_ENABLE=false
- 정상 동작
- Worker 간 Lock 경쟁 제거

### 검증 결과

멀티스레드 비활성화 이후 동일 현상이 재현되지 않았습니다.

근본적인 해결을 위해서는 Lock Ordering 정책 통일 또는 Timeout 기반 Lock 제어가 필요합니다.
